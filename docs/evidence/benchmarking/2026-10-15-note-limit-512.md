# Qualified-note admission at 512 characters

The 512-character configuration recovered all seven previously rejected
candidates without changing their text or supporting originals. The repair
update and comparison condition each ranked first in a targeted native query.
All four original handoff readers correctly reported the repair state and its
remaining literal-credential rejection. Aggregate coverage stayed at 21/24.
This fixes the observed admission loss; it does not establish incremental memory
value over source access.

## Replay results

The replay used the same six originals, 26 extraction proposals, two formal
questions, six obligations per question, and two repetitions as the previous
native-loop study. MMR stayed enabled. The HTTP reference reader and its v5
contract stayed unchanged. The new built-in profile was present, but replayed
proposals were frozen outputs from the previous extraction, not new generations.

| Measure | Previous 240-character run | 512-character replay |
| --- | ---: | ---: |
| Admitted candidates | 17/26 | 24/26 |
| Rejected for length | 7 | 0 |
| Ignored by importance/confidence policy | 2 | 2 |
| Formal obligations met | 21/24 | 21/24 |
| Complete formal answers | 1/4 | 1/4 |
| Answers retaining literal-credential rejection | 1/4 | 4/4 |
| Mean reader time | 52.97 s | 53.23 s |
| Four-reader paid cost | $0.011160790 | $0.012236165 |

The seven recovered candidates had 247 to 321 characters. Their complete
extraction objects matched the previous objects, including evidence quotes. The
stored note text also matched. The 266-character repair update and 261-character
comparison condition both passed native admission and indexing. Their targeted
recall probes each returned rank 1, and native citation checks passed. These
probes ran after formal answers and do not measure general retrieval quality.

All four formal readers read memory and cited the current repair receipt. Two
received the newly admitted repair note. The existing strict counter found an
exact memory-delivered source reference in two final answers. The other answers
used wider original windows with different reference spans. Source identity and
binding remained valid; these traces do not prove that the new note caused each
correct answer or replaced source fallback.

The three remaining formal omissions were one missing document hash/span detail
and two missing historical settled/exposure amounts. No formal answer promoted
pending native acceptance or unproved memory value to completed work. Coverage
was reviewed against the unchanged oracle by the assistant with source access;
it was not an independent or blinded assessment. These sequential, small samples
do not control stochastic output, cache state, or provider latency.

## Separate fresh-extraction diagnostic

One separate project ingested the unchanged current work receipt through built-in
profile 7. It produced three new candidates:

| Candidate | Characters | Native result |
| --- | ---: | --- |
| Repair behavior and retained exceptions | 417 | Added |
| Capture contract and calibration conditions | 520 | Rejected: `REJECT_TOO_LONG` |
| Historical budget and operating constraints | 489 | Added |

The fresh reader met all six separately frozen diagnostic obligations. It read
one memory-linked original and cited it with valid bindings. Its answer retained
the repair subject, work checkpoint, pending acceptance, and literal-credential
rejection. This single answer is not an additional matched comparison cell.

The 520-character rejection remains a failure. A larger default does not make
the model obey its declared bound, and the source fallback can hide an extraction
loss in the final answer. No candidate was truncated, regenerated, or repaired
after observing the result. The historical receipt still mentions its old
240-character operating setting; its original bytes and derived historical
statement were not rewritten to describe the new configuration.

## Protocol and deviations

- Use GPT-6 Luna through the standard OpenAI route with medium reasoning and the
  full 128000 output-token allowance. Note characters and answer tokens are
  separate limits.
- Keep Qwen3-Embedding-8B at 4096 dimensions. Reuse settled extraction responses
  and vectors only for matching recorded inputs. New vectors and all reader
  requests use the existing budget gateway. Replay preparation cost is not a
  cold-start estimate.
- Keep eight model rounds, sixteen tool calls, 32768 evidence bytes, and 12000
  bytes per tool result. Preserve the original questions, oracle, source stages,
  and shared reader. No formal cell was repeated.
- The first calibration stopped on an upstream embedding HTTP 520 before it read
  memory. Preserve that conversation, its paid chat call, and its unresolved
  embedding reservation. A separately recorded recovery calibration passed the
  actual-use and binding gate before formal execution. It still mislabeled an
  old exposure total as an unresolved reserve; this semantic error is retained.
- Run the fresh-extraction diagnostic separately. It does not repair or replace
  any replay answer. No reader/model tuning followed formal execution.

The cumulative rows are totals, not additional charges. All 67 new provider
requests are accounted for, including preparation, calibration, queries, cache
charges, and the failed request. The follow-up's $0.50 admission tranche was not
exhausted. Paid work is closed. Local compute and Codex session usage are not
priced by this provider ledger.

Both task-owned PostgreSQL/Qdrant stores passed isolated restoration. The six
replay originals and the fresh diagnostic's one reused original retained their
hashes. Both restored source and memory collections passed stored-vector queries
at 4096 dimensions. Compressed backups passed lossless file-hash checks before
the task-owned containers and volumes were removed.
