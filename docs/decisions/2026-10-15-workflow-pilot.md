# Bound the next memory trial with real maintenance outcomes

## Outcome and scope

Stop adding memory features to improve the old questions. Use those questions as
regression evidence. The next trial uses two verified maintenance gaps in ELF:
opening settlements are lost at the public budget-report boundary, and the
public verifier assumes every planned trial cell was completed. These gaps matter
when a trial carries prior cost or stops at its budget ceiling.

Each batch uses one maintenance task, two independent repetitions, three arms,
and two fresh conversations per arm. The second conversation receives a frozen
requirement update and the files left by the first conversation. All arms can
read a complete current checkout, use ordinary shell tools, edit files, run
Python checks, and maintain a handoff file. Indexed originals add ELF document
retrieval. Full ELF also adds the current native memory tools. Tool choice is
free; memory use is measured, not forced. Repository artifacts are the outcome.

These are prospective, controlled maintenance episodes. Their requirement
updates are authored test inputs, not measured human corrections or natural
customer sessions. They do not establish long-term learning or general product
superiority. Future session inputs and acceptance checks remain outside each
agent's checkout until their declared stage. Copies retain exact original Git
content and source identity. Each arm owns its edits and journal; those records
never cross into another arm.

## Execution owner

Keep this bounded experiment in the existing Python benchmark owner, as required
by the project-memory-trial decision. Reuse its native runtime, source tools,
exact-source ingestion, provider transport, and cumulative budget gateway. A
workflow mode adds only isolated file execution and a fresh conversation between
stages. It does not create a new service, scheduler, database, or general Agent
framework. The existing Python command and tests remain the execution authority;
this decision does not authorize a language or toolchain migration.

Use an existing Docker Python image for the disposable checkout. Give it no
network, host credentials, home directory, Docker socket, or other project mount.
The native tool bridge runs on the host under the existing identity and budget
controls. All arms receive the same file tools and per-session limits. Stored
notes remain derived records; the original instructions and journal are retained
separately. The application supplies source identity and ordering.

## Freeze and stop

Freeze both batches, code, base revision, model route, inputs, hidden acceptance
checks, repetitions, and thresholds before paid formal execution. Use the same
daily reader and full output allowance as the previous trial. Keep Qwen3-Embedding-8B
at 4096 dimensions. Charge preparation, journal ingestion, failures, and final
answers to the existing $10 ledger. Admit at most $1 for calibration and at most
$2 incremental exposure per batch. Do not retry a recorded conversation to improve
quality. Stop before a request whose full reservation does not fit.

A batch supports further investment only if full ELF passes all critical
integrity and scope checks and either:

- completes more final deliverables than both controls, without increasing total
  measured cost or elapsed time by more than 25%; or
- completes at least as many deliverables as both controls, with at least a 20%
  reduction in total measured cost or elapsed time against both controls, and no
  increase above 10% in the other measure.

Report each repetition and each batch. Do not pool unlike tasks to hide a loss.
Two repetitions are a product stop rule, not a significance test. If neither
batch meets the rule, stop this optimization line for this workflow and keep
ordinary file or source access as its default. Do not remove memory capabilities
from unrelated workflows on this evidence. Do not add another repair batch to
rescue the same questions.

## Acceptance and evidence

Frozen checks exercise the delivered patch in a separate evaluator. Existing
checks, scope review, and immutable-source hashes remain distinct. Score all
recorded outcomes, including incomplete work. Runtime failures do not become
semantic errors, and missing arms do not become product wins. Publish task
completion, critical errors, repeated inspection, provider cost, preparation,
latency, tool use, and actual interventions. Scripted updates are a separate
count. No live customer correction rate is measured by this test.

Retain all patches, journals, prompts, receipts, and intermediate answers. Publish
only approved project material and de-identified measurements. Keep backup and
restore evidence before removing task-owned native stores. Update current
product direction from the results even if the decision is to stop.
